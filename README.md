基于 [pzwtxdy831-commits/ST-Cache-Optimizer](https://github.com/pzwtxdy831-commits/ST-Cache-Optimizer) 的公开适配分支，保留原项目 MIT 许可及作者署名。

2.6.3 检查并修复历史识别、自动学习、世界书路由和请求旁观中的边界问题。沿用 2.6.2 独立实现的用量统计，未引入 new-api 的代码、依赖或服务，也未部署、运行或接入 new-api；本版只做离线验证，没有新增付费模型测试。

本次针对的目标流程是：**数据库辅助模型处理不同的用户输入 → 召回纪要词条 → Vertex `gemini-4-argon` 生成正文**。用户不使用泉的记忆功能，因此该兼容项默认关闭。数据库处理模型可以与正文模型不同。原有实测使用 Catie OpenAI 兼容中转的 `build-gemini-3.8-flash` 别名；本轮使用 Vertex Gemini 3.1 Flash Lite，均不能替代目标 `gemini-4-argon` 测试。

## 2.6.3 隐藏问题修复

- 历史来源：使用酒馆官方 `generate_interceptor` 只读捕获已经过宿主正则处理、尚未混入深度注入的真实聊天。引用聊天片段的世界书不再凭一小段相同文字充当历史边界；不重新执行用户正则或脚本。
- 世界书扫描：移除额外的常驻包裹条目，避免它们占用预算、提前满足最小激活数或继承快捷回复自动化。固定的非 system 深度条目和作者注释保持其原角色与位置。
- 自动学习：同名块不互相比较；按角色卡 / 群组及聊天分区，精确匹配标题，30 天过期，最多保留 50 个分区。旧版全局学习记录不再自动套用；手动配置的易变前缀仍为全局。清空学习记录也重置旧快照和计数。已激活的顶端设定按宿主来源保护。
- 请求处理：只观察同源、精确生成端点的 POST 请求；跳过需要提前求值的请求体 getter，保留代理对象提供的请求头与取消信号。收到 SSE 结束标记立即完成统计，明确的接口错误不会成为下一次比较基线。

这些回归使用合成数据和本地代码，不会发送模型请求。它们修复请求整理与统计的正确性，不代表重新测得了服务端缓存收益。

更新后需要刷新页面，让酒馆重新读取 manifest 的正式生成钩子。普通生成、重生成和滑动重试需要当前宿主来源确认；后台辅助、提示词预览、代写和 continue / assistant prefill 跳过重排。重复的真实短句通过完整楼层顺序对齐，重复引用导致边界无法唯一确认时会保守跳过。嵌套后台生成使当前来源失效时也跳过该轮，不沿用旧许可。

## 已修复的兼容缺口

- 数据库导出的纪要索引、表头、包裹可能是 `constant`，但常驻激活不代表每轮内容或召回集合不变。按数据库条目来源识别整组动态内容，不把它们提升为固定前缀。
- 识别隔离前缀 `ACU-[…]-`、`TavernDB-ACU-CustomExport-纪要-*` 等内部名字，以及经过校验的 `ACU_CUSTOM_TABLE_EXPORT_V1` 元数据。普通外部导入资料不会仅因名字带“外部导入”被归为数据库快照。
- `CHAT_COMPLETION_PROMPT_READY` 只读确认来源并重新排队；仅在带明确正文类型的 `CHAT_COMPLETION_SETTINGS_READY` 处理最终消息，覆盖数据库后续模板展开及重建消息的通常路径，避免提前改动辅助请求。
- 网络诊断排除数据库标记的内部辅助请求，按实际请求的模型、来源、接口和类型分组，只与同通道紧邻上一次请求比较。
- 分别显示“请求前缀文本相似度”和“API 缓存 token”。支持 Vertex 原生流式 `usageMetadata.cachedContentTokenCount` 与 OpenAI 兼容统计；流式响应缺少 `Content-Type` 时也按请求的 `stream` 标记识别。字段缺失显示“未知”，仅明确返回零时显示零。
- 删除截短当前聊天再模拟上一轮的检查。测试说明按钮不改聊天、不生成、不请求模型。

## 2.6.2 用量统计口径

缓存占比以响应实际返回的缓存读取 token 除以对应协议的总输入 token。各协议输入字段的含义不同：

| 协议 | 总输入 token 口径 | 缓存读取统计 |
| --- | --- | --- |
| Gemini / Vertex 原生 | `promptTokenCount + toolUsePromptTokenCount` | `cachedContentTokenCount` |
| OpenAI 兼容 | `prompt_tokens`，已包含缓存输入 | `prompt_tokens_details.cached_tokens` 等明确字段 |
| Claude 原生 | `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` | `cache_read_input_tokens`；创建量单独记录 |

同时兼容 DeepSeek 根级缓存字段和嵌套 `usage`。字段缺失仍为未知，不按 Go 整数字段默认值补零；只有明确返回零才显示零。SSE 中累计用量快照按字段存在情况更新，不能逐帧相加；异常结束的流标为未完成。缓存数大于输入时保留原始值并提示不一致，不强行截成 100%。

计算语义参考：[new-api 用量归一化](https://github.com/QuantumNous/new-api/blob/3e2ce2c8856e32ca7054d673f8cd059ae466e80c/relaykit/dto/billing_usage.go#L318-L343)、[累计快照合并](https://github.com/QuantumNous/new-api/blob/3e2ce2c8856e32ca7054d673f8cd059ae466e80c/relaykit/dto/usage_merge.go#L215)。本插件保留 JSON 字段是否存在的信息，缺失值与明确零值分开处理。

## 安装与设置

在酒馆的扩展管理中选择“安装扩展”，填入本适配分支的地址：

`https://github.com/ecyasd/ST-Cache-Optimizer`

安装后刷新酒馆。已经安装本适配分支时，可在扩展管理中更新。如果已安装原插件，可先卸载原扩展，再用上述地址安装；也可以将本包中的 `index.js`、`manifest.json`、`style.css` 覆盖到原扩展目录后刷新。手动安装时将整个 `ST-Cache-Optimizer` 文件夹放到：

`SillyTavern/public/scripts/extensions/third-party/ST-Cache-Optimizer/`

不要同时加载两份缓存优化插件。使用上面的适配分支地址安装和更新；原上游仓库独立维护。

扩展设置中保持“启用缓存优化”“世界书现场调整”“数据库召回兼容”开启。“泉记忆功能兼容”保持关闭。Vertex 建议开启流式输出，以便读取 API 用量；上游部分酒馆版本的原生非流式转换会丢失缓存统计。

动态纪要仍会发送给正文模型，其内容、关键词触发和相对顺序保留，但在提示词中的位置改变。这可能影响模型对资料的关注程度，应同时检查正文是否正常引用纪要。未识别出真实聊天范围时，发送前重排会跳过该请求。

## Gemini / Vertex 固定头强化（实验）

此开关默认关闭。仅处理来源为 `custom`（自定义 OpenAI 兼容）、`vertexai` 或 `makersuite`（Google 接口）、模型名称含 `gemini` 的普通正文请求。

开启后，将可确认的真实聊天历史之前的静态 system 消息合并到开头；除原本开头的 system 外，迁移来源的原位置保留固定 user 占位 `【固定规则已置于系统指令】`，以维持原有消息边界，避免原本被 system 隔开的签名消息被酒馆合并。历史之后的 system 消息保留原位置并转为 user。原正文内部文字不变，但规则顺序与提示优先级会改变，可能影响预设服从程度。它属于请求布局实验，不是显式缓存，也不保证服务端命中。

已知字符串形式的签名保留在原 user / assistant 消息上，不搬到其他消息。system 消息带签名、未知消息元数据、工具调用、结构化输出、媒体或其他多模态内容、已标记的数据库辅助请求、泉记忆授权标记等情况会保守跳过。无法确认真实历史、历史前仍含动态资料或历史内部仍有 system 注入时也跳过。面板会显示本次是否应用及跳过原因。

对照时先保持该开关关闭，正常推进基线轮次，再开启并继续不同输入；保持模型、连接、角色卡、世界书、预设和其余设置一致。分别检查 API 缓存统计与正文引用资料的情况。未返回缓存字段只能记为未知。

## 怎样验证正常聊天

1. 使用同一角色卡、关联世界书、预设和 Vertex 正文连接，照常让数据库处理输入并召回。
2. 正常推进至少 3 轮，每轮输入不同内容、保留上一轮回复；不要用同楼层重发相同内容代替。
3. 查看面板是否标记“连续楼层”，并读取 API 缓存 token。相同消息重发会标记“重复请求”。
4. 如需比较开关效果，分别连续观察多轮；切换后的第一轮不足以判断效果。

字符相似度不是 token 命中率。浏览器观察到的是发往酒馆的最终请求，酒馆后端还可能进行角色转换、合并和提示词后处理。实际命中以 API 响应为准。

Google 官方说明建议将大量共同内容放在前部，并在较短间隔内使用相似前缀。不能仅凭用户或中转提供的模型别名确认其缓存能力，也没有依据保证固定命中率；“系统提示变化”不能直接等同于整轮零命中。[Google 缓存说明](https://cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-overview)

2.5.2 的 24 项离线回归测试通过。该版另使用实际角色卡、关联世界书与 Izumi 预设，在 Catie 中转完成 6 次不同输入的正常完整 AI 回复，输出上限保持 30000，数据库逻辑召回及剧情推进开启。第 2—6 轮各明确报告缓存 170 token，合计 850 / 330798 输入 token，缓存占比约 **0.257%**；第 1 轮统计未留存，记为未知。该组未启用本次新增的固定头强化。

该组酒馆后端处理后的最终请求中，前 5 条完整消息保持一致，相邻请求的共同字符前缀为 68.41%—72.87%。这是字符比例，不能当作 token 命中率。没有关闭插件的对照组，不能将结果归因于插件提升。

Vertex Gemini 3.1 Flash Lite 共发送 7 次不同输入的连续请求：2 次关闭强化的基线、2 次 2.6.0 强化、3 次 2.6.1 强化。前 6 次未返回缓存字段，最后一次原生 `usageMetadata` 明确返回缓存 47051 / 输入 64305 token，约 **73.2%**，但该次只有思考、正文为空。全组为 5 次有正文、2 次空正文，未完成 6 次正常完整回答的验证目标；空正文原因未知，未保留原生 `finishReason`，不能归因于插件、输出上限或拦截。

最后 3 次原生系统头均为 60427 字符且哈希完全相同，动态记录保留在后部，签名没有新增重复。这证明了该组布局稳定，不能代替正常正文可用性验证，也不能证明相对未知基线的缓存提升。不同连接与模型的数据分组记录，不能合并为一个命中率。具体用量、观察阶段和限制见 [TESTING.md](TESTING.md)。

当前支持普通宿主正文生成。数据库零层接管的正文转发也可能带内部请求标记，不能把它未出现在诊断中当成缓存为零；其他传输和不经过当前页面 `window.fetch` 的请求同样不在观察范围内。

更多证据和预设结构见 [ADAPTATION.md](ADAPTATION.md)。原始预设的静态审查为只读，未单独执行导出文件内的脚本；实际测试使用用户已配置的酒馆环境。仓库未包含完整用户预设、角色卡、世界书或原始聊天日志。
